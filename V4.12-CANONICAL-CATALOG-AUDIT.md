# AmarangoElectro V16 — V4.12 Canonical Catalog Audit

**Gate:** V4.12 · Canonical Catalog Audit  
**Base:** V4.11 Real Catalog Read-Only Gate + V4.10 visual closure  
**Fecha de captura:** 2026-08-30  
**Estado:** auditoría real completada; producción deliberadamente NO conectada.

## 1. Resumen ejecutivo

La evidencia real permite identificar una fuente maestra para el catálogo general:

> **Fuente maestra:** `public.tienda_catalogo`, fila `id = 'catalogo'`, campo `datos` como array JSONB de 1.348 productos activos.
>
> **Read model incremental:** `public.tienda_productos_incremental`, 1.396 IDs únicos: 1.348 activos + 48 tombstones. Los 1.348 activos coinciden hoy exactamente con el snapshot maestro, incluido el payload JSON.

La función `amarango_catalogo_aplicar_delta` modifica conceptualmente el array `tienda_catalogo/catalogo`; el trigger `trg_tienda_productos_incremental` ejecuta `sincronizar_tienda_productos_incremental`, que proyecta ese array a `tienda_productos_incremental` y marca `eliminado=true` cuando un ID desaparece. **Las funciones y triggers fueron solamente inspeccionados; no se ejecutaron.**

Esta decisión **no habilita todavía producción completa**. Existen tres bloqueos que V4.12 conserva:

1. `celulares_lista/lista` contiene 92 celulares reales pero sin ID persistido por ítem, sin visibilidad explícita y sin señal de stock; no pueden entrar de manera automática a Product V16 sin inventar identidad o publicación.
2. Se detectaron 6 productos donde el snapshot dice `visible=true` y un overlay auxiliar de visibilidad dice `visible=false`. La precedencia semántica de esos overlays no está formalmente demostrada; V4.12 los excluye por **fail-closed**.
3. Las políticas RLS actuales permiten acceso muy amplio a tablas que contienen costo, proveedor, USD y otros campos internos. V4.12 no modifica RLS; por lo tanto el frontend público futuro **no debe consumir filas/JSON crudos**. Debe recibir una proyección allowlist producida por el adaptador/servidor.

## 4. Identidad canónica

### 4.1 ID recomendado

Usar como ID de fuente persistente:

- `tienda_catalogo/catalogo[].id`
- igual a `tienda_productos_incremental.producto_id`

El adaptador lo normaliza a **string** para no depender del tipo JSON number.

Ejemplos de URL estable:

- ID `-854` → `product-n854`
- ID `187` → `product-p187`

La URL no depende del nombre ni de la posición en un array.

### 4.2 Evidencia de estabilidad

- 1.348 IDs únicos en el master actual.
- 1.348 activos idénticos en incremental.
- La función de delta conserva el ID para productos de proveedor ya reconocidos.
- Los nuevos productos automáticos reciben IDs negativos nuevos y decrecientes.

**PENDIENTE:** no se dispone de historial completo multi-snapshot que pruebe que un producto manualmente eliminado y posteriormente recreado conservaría necesariamente el mismo ID. Por eso no se afirma una garantía histórica absoluta más allá de la mecánica auditada actual.

## 5. Visibilidad y eliminación

Regla V4.12 propuesta para publicación pública:

1. `incremental.eliminado=true` → **excluir siempre**, aunque `datos.visible=true`.
2. `datos.visible !== true` → excluir.
3. overlay explícito `eliminado=true`, `ocultoManualAdmin=true` o `visible=false` → excluir.
4. `ocultoManualProveedor=true` → excluir.
5. `ocultoPorDuplicado=true` → excluir.
6. stock explícitamente agotado → excluir del piloto público V4.12.
7. categoría vacía/ausente → excluir.
8. `venta <= 0` o inválida → excluir.

Datos observados:

- master `visible=true`: 564.
- conflictos master visible / overlay oculto: 6.
- visibles explícitamente sin stock: 2.
- visibles sin categoría: 7.
- candidatos estrictos luego del gate fail-closed: **550**.

La ausencia de un campo nunca se convierte en `visible=true`.

## 10. Datos públicos e internos

Principio operativo:

> El master contiene en el mismo JSON datos de venta y datos internos. Cliente y Asesor **no deben recibir el raw JSON**.

Ejemplos públicos permitidos mediante allowlist:

- stable ID técnico
- nombre
- precio de venta ARS
- categoría normalizada
- imagen HTTPS
- características comerciales públicas
- disponibilidad derivada

Internos/no frontend público:

- costo
- mayorista
- proveedor, proveedorId, proveedorCodigo, proveedorClave
- precioProveedorOriginal, monedaProveedor
- cotizacionDolar, cotizacionDolarManual, usdConvertido
- metadata de sincronización/duplicados/revisión
- `_pj` (significado no demostrado)
- objeto `datos` crudo

No se verificó un campo comercial exclusivo de Asesor dentro del master. En V4.12 Cliente y Asesor comparten la misma base Product sanitizada; futuras condiciones comerciales deberán venir de una política auditada separada.

## 11. RLS: hallazgo de riesgo, sin modificación

Las cuatro tablas tienen RLS habilitado, pero las políticas auditadas son:

- `tienda_catalogo`: `ALL` para `public`, `USING true`, `WITH CHECK true`.
- `celulares_lista`: `ALL` para `public`, `USING true`, `WITH CHECK true`.
- `productos`: `ALL` para `public`, `USING true`, `WITH CHECK true`.
- `tienda_productos_incremental`: `SELECT` para `anon,authenticated`, `USING true`.

V4.12 **no cambia RLS** por restricción del gate. Esto obliga a no conectar el frontend directamente a filas raw si se pretende preservar costo/proveedor/USD como internos.

## 13. Conclusión de gate

V4.12 puede responder con evidencia:

> **La fuente real que manda para el catálogo general es `tienda_catalogo`, fila `catalogo`. El ID persistente es el `id` de cada producto, reflejado como `producto_id` en `tienda_productos_incremental`. El incremental es un read model versionado derivado del master; `eliminado=true` es un tombstone con precedencia. Los campos públicos deben salir de un adaptador allowlist y los internos deben quedar separados.**

Pero todavía **NO** se autoriza conexión productiva porque deben resolverse humanamente la integración canónica de celulares, la política final frente a overlays de visibilidad y el mecanismo seguro de proyección pública ante la RLS actual.

**No avanzar a V4.13 por cuenta propia.**
