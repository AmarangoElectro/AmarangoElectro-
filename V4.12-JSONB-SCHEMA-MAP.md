# V4.12 — JSONB Schema Map

## Alcance y privacidad

`tienda_catalogo` es un KV store de aplicación, no una tabla exclusivamente de productos. Tiene **11 filas array, 448 object y 2 string**. Enumerar literalmente todas las claves dinámicas de cada object podría revelar identificadores o datos de otros dominios que V4.12 tiene expresamente fuera de alcance.

Por eso este documento es exhaustivo para:

1. producto master `tienda_catalogo/id=catalogo`;
2. producto envelope `tienda_productos_incremental`;
3. overlays de producto en `tienda_catalogo`;
4. ítems `celulares_lista/id=lista`;
5. banco de fotos como shape agregado.

Las filas no-producto quedan inventariadas solo por shape/propósito aparente y no se vuelcan sus contenidos.

## 1. Shapes observados

### `tienda_catalogo`

```text
id='catalogo'           datos: ProductLegacy[1348]     ← master
id='catalogo_manuales'  datos: ProductLegacy[479]      ← helper/subset
revision_manual_*       datos: RevisionOverlay         ← 216
categoria_admin_*       datos: CategoryOverlay         ← 110
visibilidad_*           datos: VisibilityOverlay       ← 48
eliminacion_*           datos: DeleteOverlay           ← 59
otras filas             datos: array/object/string     ← config/backup/control/otros dominios
```

### `tienda_productos_incremental`

```ts
{
  producto_id: string,   // PK, coincide con datos.id
  datos: ProductLegacy,
  eliminado: boolean,    // tombstone outer envelope
  version: bigint,
  actualizado: timestamptz
}
```

### `celulares_lista`

```text
id='lista'       datos: LegacyPhone[92]
id='banco_fotos' datos: Record<string, httpsUrl> // 123 entradas
```

## 4. Overlays de producto en `tienda_catalogo`

### `revision_manual_*` — 216 filas

Cada clave aparece en 216/216:

`actualizadoEn`, `ocultoManualAdmin`, `pendienteRevisionManual`, `precioActualizado`, `precioChequeadoManual`, `productoId`, `visible`.

Clasificación: Administración; `visible=false`/`ocultoManualAdmin=true` tienen efecto de gate fail-closed.

### `categoria_admin_*` — 110 filas

Cada clave aparece en 110/110:

`actualizadoEn`, `categoria`, `categoriaProveedor`, `productoId`, `usarProveedor`.

Clasificación: Administración con efecto de taxonomía. 34 de 108 overlays todavía vinculados al master tienen categoría distinta del snapshot; no se decide precedencia automáticamente.

### `visibilidad_*` — 48 filas

Cada clave aparece en 48/48:

`actualizadoEn`, `ocultoManualAdmin`, `ocultoManualProveedor`, `ocultoPorDuplicado`, `pendienteRevisionManual`, `precioActualizado`, `precioChequeadoManual`, `productoId`, `visible`.

6 productos dicen `visible=false` aquí mientras el master actual dice `visible=true`; V4.12 excluye esos IDs por fail-closed.

### `eliminacion_*` — 59 filas

Cada clave aparece en 59/59:

`actualizadoEn`, `eliminado`, `productoId`, `visibleAntesEliminacion`.

Las 59 filas vinculadas al master tienen `eliminado=true` y el master actual está `visible=false`; no hay conflicto público actual.

## 7. Shapes históricos y variabilidad

La evidencia confirma que no se debe asumir un único shape:

- el master activo tiene campos opcionales con frecuencias entre 0,07% y 100%;
- tombstones incremental conservan campos que ya no están en el master activo;
- overlays separan decisiones administrativas del objeto principal;
- celulares usan un shape completamente diferente;
- `productos` usa columnas relacionales, no JSONB.

**Regla del parser:** validar por allowlist, tolerar ausencia como `unknown/null`, nunca promover ausencia a `visible/available`, y rechazar/aislar campos inesperados en artefactos sanitizados.
